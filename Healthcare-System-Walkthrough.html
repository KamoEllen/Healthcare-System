Healthcare Management System

The Code-Anchored Walkthrough

A file-by-file explanation of how this system actually works — the request flow, the repeating patterns, the invisible glue, and every “why this over that.” Written so someone who never wrote a line of it can be dropped on any file and explain it.

Node 20 + Express TypeScript strict PostgreSQL (raw SQL) Zod JWT + refresh rotation Angular 19 Docker / K8s / Terraform

00Orientation

How to read this document

This is not a summary. It is a map you can read alongside the open files.

The existing Healthcare-System.md is ~8,700 words and topic-complete, but it explains the system in the abstract and never shows code — so when you open a real file, the prose and the file don't line up, and the invisible behaviours (the ones that live in no single file) get skipped entirely. This document fixes both problems:

  • Every claim is anchored to the real code, pasted from the actual file with its path in the header bar.
  • It is organised around journeys and behaviours, not a component inventory — because the things that confuse a newcomer (like “how does the browser's /api call physically reach the backend?”) are emergent, spanning several files that never reference each other.
  • The four Traces (sections 5–8) are the heart. If you can replay them, you can place any file on a journey — and placing a file is explaining it.
  • Section 15 is a reverse index: pick any file in the repo, find the section that explains it. Nothing is left un-covered.
The one idea that makes this learnable

The backend looks big (~40 files) but it is one 5-file template stamped 6 times, plus a handful of one-of-a-kind files. Learn the template once (section 4) and you already understand 30 files. Everything else is either a cross-cutting guard, a domain rule, or a named special.

01Mental Model

The 60-second mental model

Two programs talk over HTTP:

  • An Angular 19 single-page app (the client/ folder) that runs in the browser. It never talks to a database. It calls a relative URL, /api/v1/…, and attaches a short-lived access token to every request.
  • An Express REST API (the server/ folder) that owns all business logic and is the only thing that touches PostgreSQL — through hand-written SQL, no ORM.

Every API request walks the same straight line. No layer skips another:

router→ authenticate→ authorize→ validate (Zod)→ controller→ service→ repository→ SQL

Three organising ideas carry the whole codebase, and everything below is a consequence of one of them:

  1. Strict layering. Controllers touch req/res and nothing else; services hold the rules and throw AppError; repositories hold SQL and no logic.
  2. Every important change is audited in the same transaction it belongs to. If the audit write fails, the business write rolls back with it. This is the system's whole identity.
  3. Configuration, not code, chooses the environment. Change two env vars and the same binary runs on your laptop, on free-tier cloud, or on AWS — no code edits.

03The Repeating Shape

The pattern stamped 6 times

Every feature module is the exact same five files. Learn the roles once and you can predict what any file in appointments/, doctors/, patients/, users/, health-records/ or auth/ contains before opening it.

FileIts one jobThe tell — how you know the layer with the filename hidden
*.router.tsDeclare paths + which guards protect themcalls .get/.post/.patch, wires authenticate, authorize, validate
*.controller.tsUnwrap req, call the service, send restouches req/res; wrapped in catchAsync; no SQL, no rules
*.service.tsBusiness rules, ownership checks, throws AppErrorthrows AppError; never sees req/res; calls repositories
*.repository.tsAll SQL, parameterised; returns rowsonly SQL strings + query()/getClient(); throws no business errors
*.schemas.tsZod shapes for the request body + inferred DTO typesstarts with z.object(…); exports z.infer types

Here is the same slice of one module, top to bottom, so the chain is concrete. Notice how each file hands off to the next and refuses to do the next one's job.

1 — The router server/src/modules/health-records/health-records.router.ts

Read a router like a permission table

Each line is “method + path + who's allowed + what's validated + the handler.” You can see at a glance that only doctors create records, everyone authenticated can read, and writes are Zod-validated. router.use(authenticate) at the top means no route is reachable without a token.

2 — The controller health-records.controller.ts

Why the controller is this thin

It only translates HTTP ↔ function call: pull user, body, query params off req, hand them to the service, shape the JSON envelope. No if about permissions, no SQL. That thinness is what lets you skim a controller and instantly know “the real logic is one file over, in the service.”

3 — The service (where the rules live) health-records.service.ts

The service is the only file that says “no”

Two rules live here that exist nowhere else: only the doctor who wrote a record may edit it, and records freeze 24 hours after creation. Both are expressed as throw new AppError(…, 403). When you want to know “what are the rules of this feature,” the service is the file you read — never the controller, never the repository.

4 — The repository (SQL only) health-records.repository.ts

Why raw SQL, and why the 4-table JOIN is a feature

A health record stores only patient_id and doctor_id. To show human names the query joins patients → users and doctors → users (both people are users). With an ORM this JOIN would be hidden behind lazy relations; here it is on screen, one query, tunable. Every value is passed as $1 parameters — never string-concatenated — which is the project's SQL-injection defence.

5 — The schema (the request contract) appointments.schemas.ts

Why Zod: one declaration, two guarantees

The same z.object is used by the validate() middleware at runtime and produces the TypeScript type via z.infer. You can't let the runtime check and the compile-time type drift apart, because they're generated from the same line.

04Trace A

A request, end to end — booking an appointment

Follow one real call, POST /api/v1/appointments, through every file it touches. If you can narrate this, you can locate any backend file on the journey.

app.ts mounts router→ authenticate→ authorize('patient','admin')→ validate→ controller.book→ service.bookAppointment→ repository.create

Step 0 — the router says who may book appointments.router.ts

Three middlewares run in order before the handler: prove who you are (authenticate), check you're allowed (authorize), check the body is well-formed (validate). Only then does controller.book run.

Step 1 — the service enforces the real rules appointments.service.ts

Notice the identity translation

The JWT carries a user.id, but appointments reference a patient.id. The service bridges the two with patientsRepository.findByUserId(). This user → patient/doctor lookup recurs in every service — it's how the system keeps “who is logged in” separate from “which domain record they own.”

Step 2 — the repository writes it appointments.repository.ts

The rule has a second, stronger line of defence

The isSlotTaken check can lose a race (two patients booking the same instant). That's why the database also carries a partial unique index on (doctor_id, scheduled_at) WHERE status != 'cancelled' (section 11). If two writes slip past the service check, Postgres rejects the second with error 23505, which the error handler turns into a clean 409. App check for a friendly message, DB constraint for correctness.

The return trip is the mirror image: repository returns rows → service returns the object → controller wraps it in { status:'success', data } and sets 201 → Express serialises JSON. If any step threw an AppError, catchAsync forwarded it straight to the error handler (section 9) and none of the later steps ran.

05Trace B — the invisible one

The “BFF”: how the browser's /api call reaches the backend

This is the behaviour that no single file explains — and the one most people miss. The Angular app never hardcodes the backend's address. It always calls a relative /api/v1/…, and a different file decides where /api physically goes depending on the environment. Three files conspire; none of them import each other.

Piece 1 — the frontend only ever calls a relative path client/src/app/core/services/auth.service.ts

Two deliberate choices hiding in four lines

API = '/api/v1/auth' is relative, so the same build works in dev and prod. And the access token is stored in a private field in memory, not in localStorage — so a cross-site-scripting payload can't read it. The trade-off (the token vanishes on page reload) is paid back by the refresh cookie, below.

Piece 2a — in development, the Angular dev server proxies it client/src/proxy.conf.json

When you run ng serve (port 4200), any request the browser makes to /api/… is caught by the dev server and forwarded to the Express API on http://localhost:3000. To the browser it looks same-origin, so there is no CORS in development and cookies “just work.”

Piece 2b — in production, Vercel rewrites it at the edge vercel.json

Same trick, different layer — this is the “backend-for-frontend” seam

In prod the Angular build is static-hosted on Vercel; the API runs separately on Render. The first rewrite makes Vercel's edge forward /api/* to the Render backend — so again the browser only ever calls its own origin. The second rewrite (/(.*) → /index.html) is the SPA fallback: deep links like /appointments return the app shell instead of a 404, letting Angular's router take over. Dev uses the proxy, prod uses the rewrite; the frontend code is identical.

Piece 3 — the interceptor is the client half of auth client/src/app/core/interceptors/auth.interceptor.ts

This is why sessions feel seamless despite 15-minute tokens

Registered once in app.config.ts via withInterceptors([authInterceptor]), it runs on every outbound HTTP call: it stamps on the Bearer token, and if the server answers 401 (token expired), it calls /auth/refresh, gets a fresh access token, and transparently retries the very request that failed via switchMap. The user never sees it. The !req.url.includes('/auth/') guard prevents an infinite refresh loop when it's the login/refresh call itself that 401s.

Put together, the full “BFF” story — which lives in no single file — is: relative /api call → environment-specific forwarder (proxy or rewrite) → Express → on 401 the interceptor refreshes and replays. That's the paragraph the old markdown was missing.

06Trace C — the crown jewel

The atomic audit write

The README's headline claim is “every state change is logged atomically — if the audit log fails, the operation rolls back.” Here is exactly where and how that happens.

health-records.repository.ts — create()

Why getClient() and not the usual query()

The everyday query() helper grabs any free connection from the pool per call — useless for a transaction, where BEGIN, both INSERTs and COMMIT must run on the same connection. So transactional code checks out a dedicated client, and the finally block guarantees it's returned even if something throws — forget that release() and the pool leaks connections until the server dies.

Where else this pattern appears — and where it honestly doesn't

The identical BEGIN → write → INSERT audit_logs → COMMIT/ROLLBACK shape guards appointment status changes (appointments.repository.updateStatus, which also stores a JSON metadata blob) and the multi-table user+patient registration and password reset. Being precise: the audit trail currently covers health-record creation and appointment status transitions — appointment booking and health-record edits are not yet audited. Knowing that boundary is part of truly understanding the system.

07Trace D

The token lifecycle — issue, attach, expire, rotate

Two tokens, two very different jobs. This is the single most security-sensitive flow in the system.

TokenLifetimeWhere it livesJob
Access token (JWT)15 minutesBrowser memory; sent as Authorization: BearerProves identity on every API call — stateless, never stored server-side
Refresh token7 daysHTTP-only cookie (browser) · SHA-256 hash (database)Mints new access tokens without re-login

Issue & hash on login auth.service.ts

Why the refresh token is stored hashed

The database only ever holds SHA-256(token). If the DB is breached, the stolen hashes are useless — you can't reverse them into a usable token. The raw value exists only inside the user's HTTP-only cookie. It's the same reasoning as password hashing, applied to sessions.

Rotate on refresh auth.service.ts & auth.controller.ts

The controller sets the raw refresh token in a hardened cookie and returns only the access token in the JSON body:

The whole handshake, in one breath

Login → short JWT in memory + refresh cookie set. Access token expires after 15 min → API returns 401 → the frontend interceptor (section 6) posts to /auth/refresh with the cookie → server verifies the hash, revokes it, issues a new pair → the original request is replayed. logout revokes all of a user's refresh tokens; a password reset does the same, so a reset kicks every existing session.

The guards, and why app.ts orders them the way it does

Seven small files in middleware/ touch nearly every request. A random-file stop is likely to land here, so know each one's single job.

Two tiny files worth reading in full

Two layers of “are you allowed”

authorize is role-level (“doctors may create records”). isOwner is row-level (“you may only touch your own user id”). Services add a third, finer check — e.g. an appointment's patient must match this patient. Coarse-to-fine, and each layer assumes the one before it already ran.

The assembly — order is not decorative server/src/app.ts

Why this exact order

Middleware runs top-to-bottom. helmet is first so headers are set even on error responses. Body/cookie parsers must precede routers, or req.body and req.cookies would be empty when handlers read them. The 404 sits after all routers (“nothing matched”), and errorHandler is dead last because Express only treats a 4-argument function as an error handler, and it must be able to catch failures from every layer above it.

09Domain Rules

The five rules that make this healthcare, not generic CRUD

Anyone can build create-read-update-delete. These are the constraints that encode real clinical and compliance concerns — and they're the answers to most “why does it do that?” questions.

  1. Atomic audit trail — state changes and their audit rows commit together or not at all (health-records.repository.ts, appointments.repository.ts). See Trace C. Compliance needs a tamper-consistent record of who did what; a “log after the fact” approach can silently lose entries.
  2. 24-hour edit window — a health record freezes 24 h after creation (health-records.service.ts, EDIT_WINDOW_HOURS). Medical records are legal documents; you may fix a fresh typo, but you can't quietly rewrite history a week later.
  3. Double-defended booking — an app-level isSlotTaken check and a DB partial-unique index prevent double-booking a doctor (section 4 + 11). Two patients hitting “book” at the same millisecond must not both win.
  4. Three-role, coarse-to-fine access — patient / doctor / admin, enforced at the route (authorize), the row (isOwner), and inside services (ownership of the specific appointment/record). A doctor can only edit their own patients' records; a patient can only cancel their own pending appointments.
  5. Soft deletes — users carry a deleted_at column and every lookup filters WHERE deleted_at IS NULL (see auth.repository.ts). Historical appointments and records must keep pointing at a real person even after an account is “removed,” so rows are flagged, never physically dropped.
The appointment status machine (bonus rule)

Status flows pending → confirmed → completed, with cancelled as a terminal side-exit. The service enforces the transitions: doctors may only confirm or complete; patients may only cancel a pending one; and nothing can move out of cancelled or completed. That logic is in appointments.service.ts → updateStatus / cancelAppointment.

10Data Layer

The database & how migrations run

Nine tables, all UUID primary keys, all relationships enforced by foreign keys with ON DELETE CASCADE. A few schema decisions carry real weight:

The partial unique index that guarantees no double-booking migrations/004_appointments.sql

Why partial (the WHERE clause)

A plain unique index would permanently burn a time slot the moment anyone cancelled. Scoping uniqueness to status != 'cancelled' means cancelled appointments don't occupy the slot — it frees up for re-booking, while two active appointments still collide. The CHECK constraint on status is the DB-level twin of the TypeScript union type.

The migration runner is idempotent and transactional migrations/migrate.ts

Why this matters for deployment

You can run npm run migrate a hundred times safely: applied files are skipped, and each migration is wrapped in its own transaction, so a failure never leaves a half-migrated schema. That's what makes the CI step and zero-downtime deploys trustworthy — the same command is safe on an empty DB and a live one.

The nine tables at a glance

users (the identity root) · patients & doctors (1:1 profiles off a user) · appointments · health_records · audit_logs · and three token tables: refresh_tokens, email_verification_tokens, password_reset_tokens. A patient is a user; a doctor is a user — which is exactly why the read queries JOIN back to users twice for names.

11Runtime & Deploy

Configuration chooses the environment

The same server binary runs in three tiers with zero code changes — only environment variables differ. That flexibility lives in two files.

Every setting is validated at boot server/src/config.ts

Why validate env vars with Zod and exit(1)

A missing DATABASE_URL or a 12-character JWT_SECRET is a misconfiguration you want to discover at startup, not three requests later in production. The server refuses to boot rather than run insecurely — and the same getEmailConfig() switch turns EMAIL_PROVIDER into Mailtrap, Resend, or AWS SES transport settings. Swap the tier by swapping DATABASE_URL + EMAIL_PROVIDER; nothing recompiles.

TierDatabaseEmailCompute
LocalDocker Postgres 15Mailtrap (catches all)localhost via docker-compose
Free prodNeon (0.5 GB)Resend (3k/mo)Render / GitHub Actions
ScaledAWS RDS (Multi-AZ)AWS SESAWS EKS + Terraform

CI gates every push .github/workflows/ci.yml

On push/PR to main, GitHub Actions spins up a real postgres:15 service, then runs, in order: tsc --noEmit (type check) → migrate:test (prove migrations apply cleanly) → npm test (Jest + Supertest against the live DB, 80% coverage floor). A type error, a broken migration, or a dropped test all block the merge. server.ts handles the deploy side — SIGTERM triggers a graceful drain so Kubernetes can roll pods without dropping in-flight requests.

13Honesty

Where the docs disagree with the code

These are the contradictions a newcomer can't discover on their own — and the highest-value context in this whole document. When docs and code disagree, the code wins.

  • Folder layout. The older architecture notes (and the hi.html decision tool) describe top-level routes/ controllers/ services/ repositories/ folders and a server/src/frontend/ directory. The real code is organised by feature: server/src/modules/<name>/ with the five files co-located, and there is no frontend/ folder. Trust modules/.
  • API prefix. Prose sometimes writes /api/…; the app actually mounts everything under /api/v1/… (app.ts). The proxy and Vercel rewrite both match on /api, so the versioned paths still flow through.
  • Audit coverage. The README says “every state change is logged.” Precisely, audit rows are written for health-record creation and appointment status changes. Appointment booking and health-record edits aren't audited yet — a real gap worth knowing, not glossing.
  • Session persistence across reload. The access token lives in memory, so a full page refresh drops it. The refresh cookie can re-mint one, but the code shown doesn't auto-refresh on app bootstrap — so a hard reload can bounce you to login until the next call triggers the interceptor. Good to know before you “fix” a non-bug.

16The Rationale

Justifying every decision made

Every choice here reads the same way: do X, so that Y — not Z, because Z would cost you W.

The sections above explain what the system does and how. This one answers why — for the tools and for the design decisions, including the ones that changed mid-build. Read against section 12 (the compact ledger): that's the summary table; this is the reasoning, with the failure each decision prevents.

The two things every decision optimises for

Notice the pattern as you read: nearly every choice buys either visibility (you can see exactly what runs — the SQL, the middleware order, the query plan) or safety (fail closed, fail loud, and always leave a record). When a tool would trade either away for convenience, it was rejected.

Part B — Decisions that changed mid-build (and why)

These weren't right the first time. Each is framed as started with → changed to → so that, which is the most honest kind of justification — it shows the failure that forced the change.

1  ORM → raw SQL

Started intending to use Prisma.

Changed to raw SQL after writing the first multi-table appointment JOIN.

So that the query stayed readable and correct — Prisma's API needed workarounds for that exact JOIN shape, in more lines and with less visibility.

2  Raw refresh token → SHA-256 hash

Started planning to store the raw refresh token string.

Changed to storing only its hash, after a threat-model review — before any code was written.

So that read access to the database is worthless to an attacker: raw tokens are instantly usable, hashes are not.

3  Hardcoded SMTP → EMAIL_PROVIDER env var

Started with Mailtrap SMTP settings hardcoded for dev.

Changed to provider auto-selection from one env var.

So that the same codebase ships to every tier with only credentials supplied — no code edits between dev, free-prod and scaled.

4  Audit-after → audit-inside the transaction

Started writing the audit-log insert after the main action.

Changed to the same BEGIN…COMMIT as the action itself.

So that you can never get a state change with no record of it: if the audit insert fails, the business write rolls back too. → Trace C.

5  No window → 24-hour edit window on records

Started with freely editable health records.

Changed to freeze a record 24 hours after creation.

So that medical records — legal documents — can't be quietly rewritten days later; corrections happen promptly and stay in the audit trail. → section 9.

6  In-memory slot filter → database COUNT + unique index

Started by fetching a doctor's appointments and filtering in memory to check availability.

Changed to a single COUNT(*) query, backed by a partial unique index.

So that two simultaneous bookings can't both pass the check — the in-memory version had a race; the DB constraint can't. → sections 4, 10.

7  Two configs → three named tiers

Started with just a dev config and a prod config.

Changed to development → free-tier production → scaled production.

So that there's a real deployment path with no credit card (Neon + Resend) — the gap between “works locally” and “works for users” was too large to skip. → section 11.

8  Per-service ownership checks → isOwner middleware

Started handling “is this your row?” inside each service.

Changed to one dedicated middleware comparing params.id to user.id.

So that horizontal privilege escalation (one patient editing another via PATCH /:id) is blocked consistently in one place instead of re-implemented per route. → section 8.

The through-line

Read together, the tooling and the course-corrections tell one story: prefer the option you can see and verify, and when in doubt, fail safe and leave a record. Raw SQL over a hidden ORM, a DB constraint over an app check, audit inside the transaction, hashes over raw tokens, one binary configured by environment — every decision is the same instinct applied to a different layer. That instinct is the real thing to take from this codebase.
